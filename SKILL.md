# Рабочий процесс команды

Общий процесс для любого проекта. Общие правила владельца (скрипты вместо модели, субагенты и бюджет, автор не утверждает сам себя, браузер, память) лежат в `~/.claude/CLAUDE.md` — здесь они не повторяются, только развиваются. Правила самого проекта (governance, аудит контрактов по триггерам, слияние кода) — «по правилам проекта»: они сильнее этого навыка.

Навык — git-клон приватного репозитория `PavelSlaven/team-process` в `~/.claude/skills/team-process`. Правку навыка автор коммитит и пушит в той же задаче; проектные пути, номера решений и примеры с файлами проекта сюда не пишутся — они в памяти и журналах проекта.

## 1. Когда применять

- Задачу делает не ты сам, а исполнитель (Codex, Cursor, Claude Sonnet на сервере) или субагент.
- Нужен цикл «задание → план → работа → сдача → ревью → PR».
- Планируешь запуск нескольких агентов, бюджет токенов, ежедневный разбор.
- Не применять: мелкая правка, которую быстрее сделать самому; разовый вопрос.

## 2. Роли

- **Владелец.** Решает по продукту, нормам, необратимому, продакшену; ставит приоритеты. Мелочами не занимать. Решение владельца записывать в тот же день (см. §9).
- **Ведущий-ревьюер** (главный чат Claude). Помнит всю цепочку, пишет задания, отвечает на вопросы исполнителей только по технике (продукт, нормы, необратимое и продакшен — владельцу), ревьюит каждую сдачу, ведёт git, PR и слияние по правилам проекта. Не исполнитель: объёмную работу отдаёт вниз. Ведёт текущий план (§3 п. 0); свой обещанный «следующий шаг — мой» в том же ходе записывает туда, сделал — отмечает (у своего шага нет входящего события).
- **Заместитель ведущего** (владелец). Те же права, делёж по потоку, у дела один хозяин. Ведущий: владелец, нормы, git и слияние, PLAN на контракты, схему БД, промпты LLM, финал. Заместитель: прочие PLAN, BENCH-OK, флот, загрузка помощников; не сливает. Задача помечена хозяином, её события будят только его; чужое — блоком другому.
- **Исполнители.** Codex (руководитель — `gpt-6.1-sol` `high`, сам ведёт своих субагентов — всегда `gpt-6-luna` `xhigh`; `astra` не используем; без caveman; малый аккаунт — только `luna`, разведка; §7), Cursor (`composer`), Claude Sonnet. Каждый в своей рабочей копии и ветке. Общаются только файлами задачи: мостом флота или в прямом режиме (§4).
- **Субагенты Claude.** Чтение, сборы, подсчёты, прогон тестов и выжимки логов, код по ясному брифу, первый проход проверок. Без вложенных; каждому своя временная подпапка (§9).
- **Помощники — постоянные сессии Claude со своей ролью** (например: ревью, тексты для пользователя, стенды, мониторинг); состав — в памяти проекта. **Любой план, разбор очереди или оптимизация называет исполнителя каждого пункта среди всей команды:** помощники, исполнители, распорядитель, скрипты — а не только ведущий и флот. Помощник работает файлами в своей папке, ведущему отправляет один отчёт на пачку. Модель помощника — по доле суждения в роли: мониторинг и механика — Sonnet.
- **Правила помощника:**
  - Файл роли начинается с миссии словами владельца; дальше порядок работы, «не моё», первое действие после старта. Состояние — отдельным файлом, история — в архиве.
  - Работает только по миссии и поручениям ведущего или владельца. Поручение, которое меняет роль, ведущий сначала вносит в состав команды (roster).
  - Дел нет — тишина: не опрашивает, задач себе не придумывает. Свои пилоты, эксперименты и правки общих файлов (этот навык, CLAUDE.md, README, чужие инструменты) — только после «да» ведущего или владельца.
  - Проверка сдачи — один круг; повторный круг того же рода — стоп и вопрос.
  - Команды, способные спросить разрешение, без владельца у экрана не запускать; удаление — списком ведущему.
  - Не хватает данных или неясна норма — вопрос ведущему; затрудняется он — владельца спрашивает он сам (§9). Сам не реконструирует и не придумывает.
  - Владельцу сам не пишет: вопрос — ведущему (§9 «Вопросы владельцу»).
  - Закончил задачу — состояние в файл роли и `clear_session("self")`; внутри задачи — compact.
- **Независимые проверяющие.** Не автор, не исполнитель. Два уровня (решение владельца):
  - **Промежуточные проверки** по ходу задачи: аудит контрактов по триггерам, повторные раунды после исправлений, первичное утверждение данных. Их делают скриптовый разбор сдачи ведущим и проверяющий другой семьи моделей: работу Codex — субагент Claude Opus, работу Claude — Codex `gpt-6.1-sol` (из моделей Claude ревьюит только Opus).
  - **Opus 5.5 `xhigh` сверх промежуточной проверки работы Codex — только в двух случаях.** (1) Финал: приёмка перед слиянием или закрытием задачи, итоговое утверждение данных. (2) Тупик: исполнитель не может решить проблему. Признаки тупика: 3+ итерации без сходимости; второй REJECT или BLOCK того же рода; исполнитель сам пишет, что не может. Opus по ходу работы и на каждый READY не запускается.
  - **Застой:** 3 ч без закрытого шага у задачи в работе по текущему плану (§3 п. 0) — отдельный аудитор застоя (Opus 5.5 `xhigh`): почему не движется процесс; новых кругов до вердикта нет. Ведущий сверяет время последнего закрытого шага при старте сессии, каждом запуске и закрытии.
  - **Opus проверяет работу, а не выводы** (§3 п. 7).

## 3. Жизненный цикл задачи

0. **Запуск задачи.**
   - **Текущий план.** У проекта один живой список работы; где он — в памяти проекта. В нём цель, задачи по порядку, у каждой исполнитель, статус, время последнего закрытого шага и что ждёт владельца. Запись задачи хранит только текущее состояние: при смене статуса значение заменяется, история статусов не дописывается. Ведёт ведущий: правит при каждом запуске, закрытом шаге и закрытии задачи. По нему сверяют планы исполнителей, застой (§2) и разбор (§10).
   - **Карточка запуска.** До запуска любой задачи (исполнителю, помощнику, армии субагентов как отдельной задаче; субагенты внутри одобренной задачи — без карточки) ведущий пишет карточку файлом и показывает владельцу её суть:
     - что и зачем — пункт текущего плана;
     - как — шаги: кто делает, модель и `effort`, что на выходе и в какой форме (п. 2, п. 5);
     - источник истины по каждому пункту;
     - лимиты Claude и Codex числами, с временем снимка (§7); были запуски после снимка — снять заново;
     - проверка задания: для задания на проверку или со сложным правилом — пути враждебного чтения и пересказа (п. 1; это подготовка карточки, своей карточки не требует), иначе «не требуется: <почему>»;
     - вопросы владельцу (§9), у каждого — где искал ответ;
     - чего задача не делает.
   - Запуск — после ответа владельца. Шаги внутри одобренной задачи нового «да» не требуют; смена подхода или рамки — новая карточка.
1. **Самодостаточное задание.** Задача = issue/CR в репозитории + пути в репозитории; мост только канал сообщений. В задании: цель, источник истины по каждому пункту, что не трогать, чем проверять, режим (ниже), правила из §5. Задача по логике продукта — раздел «Механизм и владелец»: общий механизм, владелец, почему не частный случай, ≥3 разных случая класса. Починка — класс ошибки, не экземпляр; третья починка одной темы за 7 дней — сначала архитектурный пересмотр.
   - **Задание читают буквально (владелец).** Исполнители и субагенты делают задание дословно, противоречие молча обходят, решают по-своему или стоят. Задание — подробное и однозначное: точные пути, рамка правок, исключения из запретов, критерий готовности, чем проверить, что делать при конфликте с кодом («сообщи, тест не ослабляй»). Обязательное для исполнителя правило — текстом в задании: ссылку в списке источников исполнитель не открывает. Перечитать самому мало: автор своих дыр не видит. Задание на проверку (страж, валидатор, приёмочный тест) или со сложным правилом до запуска (пути результатов — в карточке запуска, п. 0):
     - **сверяется с каталогом ловушек** `briefs.md` в папке навыка;
     - **враждебно читает не автор** (задание Claude — Codex sol): ищет дословное исполнение, при котором запрещённое проходит или честное отвергается, и пишет атаки на цель — входы, которые нарушают цель, и честные случаи, которые должны пройти. Они входят в таблицу доказательства задания красными и зелёными случаями;
     - **пересказывают две модели разных семей**: PLAN исполнителя и независимый пересказ другой семьи, который PLAN не видит (задание Codex — субагент Claude, и наоборот). Ведущий сверяет их до `PLAN-OK`; расхождение в понимании — дыра в тексте: правится задание, а не план.

     **Буквальный язык (владелец).** Задание и план пишутся так, чтобы каждое требование допускало одно прочтение — то, которое имел в виду постановщик. Вместо слов «по возможности», «при необходимости», «и т. п.», «и подобное», «аналогично», «как обычно», «как сейчас», «разумно», «где уместно», «лучше» — точный список, условие или число. Вместо «это», «там», «такой», «он» без ясного предмета — название предмета. Каждое действие называет объект, место (путь файла и раздел или строку в нём; для команды — рабочую папку) и признак выполнения. Перед отправкой постановщик перечитывает каждую фразу с вопросом «можно ли выполнить это иначе, чем я имею в виду?»; если можно — переписывает фразу (дословную цитату владельца не меняет — уточняет рядом).

   - **Чистый вход (владелец).** Постановщик отвечает, чтобы исполнитель получил только задание, правила проекта и нужные пути. Проверка — скриптом внутри запуска: проба при смене отпечатка запуска (скрипт, конфиг, глобальные файлы, бинарь, папка), отказ при чужом, сверка снятого входа (rollout, запрос) после каждого прогона, с помощниками. Флаги «отключить плагин» не доказывают чистоту — только снятый вход. В нём не должно быть:
     - чужих инструкций: глобальные AGENTS.md/CLAUDE.md домашних папок, чужие skills, внерепозиторные брифы;
     - лишних логов и чужих задач.
   - **Вход субагентов Claude (владелец).** Workflow — только когда последнее сообщение чата — запрос владельца на эту самую работу, иначе Agent; после запуска — `tools/check-subagent-input.mjs`, FAIL — результаты не принимать. Почему и как — `fleet.md` §7 «Вход субагентов». Бриф субагента — файлом, в промпте путь: после сжатия контекста у субагента остаётся пересказ промпта, а не его текст.
   - **Субагенты в задании (владелец).** Раздел «Субагенты»: механика списком — поиск, чтение, прогон тестов, выжимки логов, сверки, код по ясному брифу — и строка «вызови навык `team-process`». Модели — по общим правилам («Субагенты и бюджет»).
2. **PLAN.** Исполнитель до правок присылает `## PLAN-<id>`: каждое требование своими словами, источник истины, что изменит, чем проверит, развилки с рекомендацией, объём, чего решение не закроет. Два режима:
   - **«План у ревьюера»** — всё, кроме режима ниже, включая тесты и проверки. Исполнитель стоит до `PLAN-OK-<id>`. `PLAN-CHANGES-<id>` — доработать. Смена подхода по ходу — `PLAN-<id>-delta`.
   - **«Ведёт sol»** — исследования, черновики данных, разведка. Ведущая модель исполнителя сама делит работу, одобряет внутренние планы, пишет PLAN для записи и не стоит. Стоп только на `DONE` или на `Q`. Ревьюер проверяет итог.
   - Без плана — только механические шаги, продиктованные дословно.
   - **Колонка «кто делает»** у каждого шага: сам, субагент (модель) или скрипт. Сам — суждение, план, итоговая сверка; механика — субагенту или скрипту. Нет колонки или механика у «сам» — `PLAN-CHANGES`. План добавляет цель или результат, которых нет в задании, — тоже `PLAN-CHANGES`; шаги реализации требуемого результата добавкой не считаются. План исполнителя пишется тем же буквальным языком (§3 п. 1): фраза плана, которую можно понять двумя способами с разным результатом, — тоже `PLAN-CHANGES`.
   - **Стенд** (работа опирается на нейросеть: промпт, формат пакета, выбор модели). Полный текст — `bench.md` в папке навыка; читать перед BENCH-PLAN и BENCH-OK. Кратко: малый стенд в PLAN обязателен; запуск только по `BENCH-OK` ведущего после его личного разбора провода — SHA `wire-review` и аудита состава, пять строк «данные / вид / путь / куда / объём-дубли-порядок»; облачная проба первой; пилот формы данных до массового наполнения; вход стенда = контракт роли и код продукта; каждый фактор — во входе каждой руки; тексты случаев читать все.
   - **Промпт-ревью.** Каждое изменение промпта, проекции входа роли или параметров роли сдаётся с `prompt-review-<роль>.md`: полный system + user + params «до/после», снятые из фактического запроса к провайдеру. Ведущий читает его лично и целиком (не субагент) до CLOSE и коммита; замечания возвращает с файл:строка.
3. **OK.** Отвечай на PLAN быстро: исполнитель простаивает. Ответ, отправленный во время прогона, исполнитель не увидит — отправляй после остановки (§4).
4. **Работа test-first.** Сначала красный тест, потом код. Самоаудит — один круг (§5).
   - **Приёмочные тесты пишет старшая модель до начала (решение владельца).** Для кодовой задачи — Codex sol, а не исполнитель: до старта, по описанию поведения из задания. Тесты фиксируются хэшем; исполнитель их не меняет (правка — `Q`), неверный тест правит старшая модель. Перед заморозкой тест краснеет по заявленной причине; цель проверяется и поведением в настоящей среде; каждому шагу — свой тест. Подробно — `checks.md` §6 «Приёмочные тесты старшей модели».
5. **DONE.** Блок `## DONE-<id> | время | HEAD <sha>`:
   - таблица «пункт → коммит → тест → лог красный/зелёный»;
   - числа только из логов, а не из памяти;
   - фактическое время прогонов;
   - раздел «не проверено» (обязателен, пустой не бывает без пояснения);
   - свои вызовы и вызовы субагентов — числами скрипта по транскрипту сессии (путь — в памяти проекта); ведущий сверяет тем же скриптом;
   - `git status`; для данных — скриптовый список изменённых строк (id, столбец, старое → новое). Неперечисленное изменение — дефект сдачи.
6. **Ревью скриптами.** Ведущий проверяет сдачу детерминированно (§6), а не «читаешь и веришь». Заявленный зелёный прогон без лога — не прогон.
7. **Независимая проверка** — по уровням §2. Автор не утверждает себя.
   - **Opus: один проход в финале или при тупике.** Проверяет не только DONE и выводы исполнителя, но и саму сделанную работу. Пакет Opus:
     - diff;
     - сами артефакты — промпты и входы ролей, снятые с провода (`prompt-review-<роль>.md`), строки данных, случаи стенда, сырые ответы модели, логи прогонов;
     - задание и исходный план.
   - **Opus обязан:**
     - открыть артефакты сам и выборочно проверить качество работы по существу, а не по отчёту;
     - воспроизвести ключевые цифры;
     - в вердикте ссылаться на файл:строку артефакта, а не на текст сдачи.
   - Вердикт, опирающийся только на DONE, — не проверка.
   - **При тупике Opus** сначала ищет, не в работе ли исполнителя причина: промпт, проекция, данные, стенд. Только потом — в модели или задаче.
8. **PR → CI → слияние** (§8).
   - **Закрытие.** Сразу после слияния или приёма исследования — отметка в текущем плане (п. 0) и закрытый issue. В режиме флота ещё блок `## CLOSE-<id> | время | принято; слито в #N` в мост: без него задача остаётся на доске «ждёт ревьюера».
9. **BLOCK / rework.** Ответ `REVIEW-<id>` с точными пунктами и путями (файл:строка, что не так, что ожидается). Не «переделай», а список.
   - **Причина каждого REJECT и BLOCK.** В вердикте — поле «причина»: задание, исполнитель, приёмочный тест, данные или среда; его заполняет проверяющий (строка в каждом брифе проверки). Причина «задание» — ведущий в тот же день дописывает ловушку в `briefs.md`: ловушка, пример (файл:строка), как писать. При закрытии задачи (п. 8) ведущий сверяет: у каждого её возврата есть причина в журнале причин, у причины «задание» — ловушка в `briefs.md`.
10. **Стоп-правила.**

## 8. Git, PR и CI

- Ветка на шаг; PR маленькие; коммит-сообщения обычным языком.
- Без стопок PR: принятое — сразу в main, в ветку части продукта ежедневно вливать main.
- Если из среды исполнителя пушить нельзя (например, токен только для чтения) — **relay**: `git fetch ssh://host/path <ветка>` локально, затем `git push origin FETCH_HEAD:refs/heads/<ветка>`.
- Перед коммитом на сервере: `set -e`, переменные — отдельными шагами до цепочки `&&`, проверить `git branch --show-current` (ветка рабочей копии может не совпадать с ожидаемой).
- В каждый PR: строка в журнал изменений, `Closes #N` по правилам проекта, отчёт по формату проекта. Подтверждённые ловушки — в реестр ловушек проекта, а не только в память.
- Правки нормативных документов проекта (governance) не входят ни в какие разрешения на слияние: только по прямому запросу владельца в текущей задаче.
- Слияние — после независимой проверки (если она требуется) и зелёного CI. Что сливает ревьюер сам, а что только владелец, определяют правила проекта и записанные разрешения владельца.
- **CI-наблюдатель** ищет прогон по SHA головы ветки, а не «последний». `cancelled` — не падение (замещён новым push); падение = `failure`.
- Параллельные PR конфликтуют на журнале изменений и сгенерированных статусах: следующий PR обновить на main (merge, не rebase, если так решено для ветки) и пересобрать генерируемое.
- Тесты, использующие одну и ту же локальную БД, не запускать параллельно — ни в одной рабочей копии, ни в нескольких.

## 9. Безопасность и владелец

- Общая машина — по §5; чужими сервисами пользоваться как клиент можно, чужие данные не трогать. Секреты и токены не коммитить.
- Широкие destructive-команды запрещены (см. правила проекта): `git clean`, `reset --hard`, `checkout -- .`, `restore .`, `rm -rf .` — и любая команда, которая удаляет или откатывает всё дерево рабочей копии.
- **Сначала владельцу.** Результаты исследований, каталоги, наборы правил, изменения процесса показываются владельцу с явными точками решения; в документы, issue и PR они попадают, и работа от них запускается, только после его OK. Фильтр аудиторов владельца не заменяет. Рутинное ревью сдач при разрешённой владельцем автономной работе можно проводить без предварительного показа владельцу.
- **Вопросы владельцу и журнал решений.** Пути проекта — в памяти проекта.
  - Задаёт только ведущий; помощники и исполнители передают вопрос ему.
  - До вопроса — поиск ответа: единый документ проекта, журнал решений, контракты и правила, по-русски и по-английски. Нашёл — ссылка, а не вопрос.
  - Вопрос — кратко: контекст 1–3 строки, где искал, варианты и рекомендация первой; пачкой, сложное — файлом.
  - Ответ — дословно в тот же день: журнал решений проекта плюс репозиторий (решения по продукту — в журнал решений продукта, процессное — issue или комментарий). Не хранить только в чате или мосте.
  - Ответа нет или «позже» — пункт в реестр открытых вопросов проекта; предложение ведущего помечено как предложение.
- **Каждая найденная проблема и всё отложенное — свой issue в тот же день (решения владельца).**
  - **Что считается.** Находки аудитов (включая аудит контрактов), ревью, стендов, прогонов и ежедневного разбора. Всё, что решено «позже», «на следующем этапе» или «после X».
  - **Исключение.** Без отдельного issue остаётся только находка ревью, которую исправляют в той же задаче до её закрытия; её ведёт issue этой задачи.
  - **Что в issue:** что не так или что отложено; почему; условие возврата; источники (файл:строка).
  - **Чего недостаточно:** строки в отчёте, мосте или общем плане.
  - **Для исполнителей.** Исполнитель перечисляет находки вне задачи в сдаче, issue заводит ведущий.
  - **Закрытие.** Общий план не закрывает отложенные пункты: каждый закрывается, когда решён.
- **Блокировку классификатора автомода** не обходить: объяснить владельцу, что заблокировано и почему, и ждать решения.
- **Инструмент с побочными эффектами** (флот, монитор) менять только после остановки монитора, который его вызывает; иначе смена бинарника запускает побочные действия сама. Подменять скрипты атомарно (`.new` → `mv`), запущенный bash читает файл лениво.
- **Субагенты и временные папки.** В каждом промпте, разрешающем временные файлы: своя подпапка `<scratchpad>/<метка>/`, «удалять только её, ничего другого в scratchpad не трогать».
- Каждому решению владельца «да» сопоставлять пункт — не додумывать шире сказанного.
- **Браузер и память** — по общим правилам `~/.claude/CLAUDE.md`.

# Рабочий процесс команды

Общий процесс для любого проекта. Общие правила владельца (скрипты вместо модели, субагенты и бюджет, автор не утверждает сам себя, браузер, память) лежат в `~/.claude/CLAUDE.md` — здесь они не повторяются, только развиваются. Правила самого проекта (governance, аудит контрактов по триггерам, слияние кода) — «по правилам проекта»: они сильнее этого навыка.

Навык — git-клон приватного репозитория `PavelSlaven/team-process` в `~/.claude/skills/team-process`. Правку навыка автор коммитит и пушит в той же задаче, вместе с той же правкой в `codex/` — версии навыка для Codex (README); проектные пути, номера решений и примеры с файлами проекта сюда не пишутся — они в памяти и журналах проекта. Файлы тем (`fleet.md`, `checks.md` и другие) лежат в папке навыка; файл темы читать перед работой с ней.

## 0. Ядро

**Рой и буквальный язык (владелец).** Всегда разбивай задачу на независимые части и раздавай исполнителям с субагентами — пусть работают роем: нити Codex обоих аккаунтов (помощники `gpt-6-luna` `xhigh`) и Cursor параллельно, сервер загружай до предела. Все задания и промпты — буквальным языком: одно прочтение, без возможности толковать иначе.

а) **Роли (владелец).** Ведущий Claude Opus ставит план, утверждает PLAN и сдачи, запускает исполнителей и субагентов. Итоговое ревью задачи — один проход Opus 5.5 `xhigh`: его делает сам ведущий, с субагентами на чтении и сверках, или Opus-субагент по заданию ведущего; ещё один — только при тупике (признаки: §2). Чтение, вычитку и сверки он поручает субагентам и скриптам: Haiku — рутина, разведка, чтение, сверки, простой код; Sonnet — вычитка на двусмысленность и сложный код; вычитку PLAN и заданий, проверку буквального языка и двусмысленности делают субагенты, `tools/check-literal.py` и пересказ другой семьи моделей по `briefs.md` «Буквальный язык и организация работы». Сам и целиком ведущий читает: `prompt-review-<роль>.md`, вопросы `Q` и те места PLAN, DONE и diff, которые субагент или скрипт отметил как расхождение или развилку; на итоговой проверке — артефакты по §3 п. 7. Остальное чтение — через субагентов.

б) **Codex (владелец).** На основном аккаунте любой ведущий Codex — нить-исполнитель на сервере или интерактивная сессия — только `gpt-6.1-sol` `high`, его субагенты — только `gpt-6-luna` `xhigh`; на малом аккаунте — только `gpt-6-luna`, разведка. Чтение, разведку, сверки и рутину ведущий Codex поручает субагентам `gpt-6-luna` `xhigh` и скриптам, сам — суждение, план и итоговая сверка; эти правила идут текстом в задании. Ведущий Codex запускает сразу все независимые дорожки, не больше свободных мест среды (число — предел потоков запуска, адрес — в памяти проекта); раздел „Организация работы“ задания делит механику на независимые дорожки. Работу ради занятости мест не придумывает, зависимое не дробит. Раз в 30 минут скрипт проверяет загрузку Codex, работу нитей и разбиение плана — `fleet.md` «Проверка загрузки Codex».

в) **Лимиты (владелец).** Перед каждой задачей — лимиты Claude и Codex числами со временем снимка. Тогда же ведущий запускает `tools/usage-daily.py` с `--alarm` из памяти проекта. Код 3 (`ТРЕВОГА`) — до запуска задачи ведущий по выводу сверяет процесс с правилами: каждый Opus-субагент — итоговый проход или тупик, механика ведущего отдана субагентам и скриптам; нарушение исправляет, затем запускает задачу.

г) **Итоговый проход Opus (владелец).** Один на задачу, по а); ещё один — только при тупике, признаки — в §2. Повторный проход Opus после исправлений запрещён, кроме тупика по §2: исправления проверяют и скрипты, и отдельная нить Codex `gpt-6.1-sol` — оба. Черновики и наполнение данных Opus-субагенту не поручаются; итоговое утверждение данных — поручается.

д) **Чтение файлов тем.** В таблице «Claude» — исполнитель и субагент Claude: читают сами целиком до действия; «Opus» — ведущий: поручает чтение и сверку субагенту и получает выжимку. Исполнитель Codex и субагент luna читают файл темы сами целиком до действия; Opus-субагент — как «Claude». Проверка чтения — §3 п. 1 «Прочитать до работы».

| действие | файл темы | кто читает |
|---|---|---|
| Задание исполнителю | `executor-rules.md` | Claude; Opus — через субагента |
| Мост, запуск, надзор, лимиты, git, ежедневный разбор | `fleet.md` | Claude; Opus — через субагента |
| Тесты, проверки, промпт-ревью | `checks.md` | Claude; Opus — через субагента |
| Раздел «Стенд» в PLAN, BENCH-OK | `bench.md` | Claude; Opus — через субагента |
| Папка задачи, DONE, закрытие | `cleanup.md` | Claude; Opus — через субагента |
| Задание, PLAN, бриф | `briefs.md` | Claude; Opus — через субагента |
| Запись уроков | `lessons.md` | Claude; Opus — через субагента |

## 1. Когда применять

- Задачу делает не ты сам, а исполнитель (Codex, Cursor, Claude Sonnet на сервере) или субагент.
- Нужен цикл «задание → план → работа → сдача → ревью → PR».
- Планируешь запуск нескольких агентов, бюджет токенов, ежедневный разбор.
- Мелкая правка, которую быстрее сделать самому, и разовый вопрос исключены.

## 2. Роли

- **Владелец.** Решает по продукту, нормам, необратимому, продакшену; ставит приоритеты. Мелочами не занимать. Решение владельца записывать в тот же день (см. §9).
- **Ведущий-ревьюер** (главный чат Claude). Помнит всю цепочку, пишет задания, отвечает исполнителям только по технике (продукт, нормы, необратимое и продакшен — владельцу), ревьюит каждую сдачу, ведёт git, PR и слияние по правилам проекта. Не исполнитель: объёмную работу отдаёт вниз. Ведёт текущий план (§3 п. 0); обещанный «следующий шаг — мой» в том же ходе записывает туда, сделал — отмечает (у своего шага нет входящего события).
- **Заместитель ведущего** (владелец). Права те же; делят поток, у дела один хозяин. Ведущий: владелец, нормы, git и слияние, PLAN на контракты, схему БД, промпты LLM, финал. Заместитель: прочие PLAN, BENCH-OK, флот, загрузка помощников; не сливает. У задачи указан хозяин, её события будят только его; чужое — блоком другому. Вопрос с рекомендацией заместитель решает сам; ведущему — защищённое, удаление, деньги и доступы, слияние, нормы, контракты и промпты, PLAN-OK и приёмка ведущего, вопрос без рекомендации, застой; его решения ведущий смотрит на ревью (владелец).
- **Исполнители.** Codex (модели и аккаунты — §7; без caveman), Cursor (`composer`), Claude Sonnet. Каждый в своей рабочей копии и ветке. Общаются только файлами задачи: мостом флота или в прямом режиме (§4).
- **Субагенты Claude.** Чтение, сборы, подсчёты, прогон тестов и выжимки логов, код по ясному брифу, первый проход проверок. Без вложенных; каждому своя временная подпапка (§9).
- **Помощники — постоянные сессии Claude со своей ролью** (например: ревью, тексты для пользователя, стенды, мониторинг); состав — в памяти проекта. **Любой план, разбор очереди или оптимизация называет исполнителя каждого пункта всей команды** (помощники, исполнители, распорядитель, скрипты), не только ведущего и флот. **Колонка «кто делает»** у каждого шага: сам, субагент (модель) или скрипт; нет колонки или механика у «сам» — `PLAN-CHANGES`. Помощник работает файлами в своей папке, ведущему отправляет один отчёт на пачку. Модель помощника — по доле суждения в роли: мониторинг и механика — Sonnet.
- **Правила помощника:**
  Полный текст — `fleet.md`, «Файл роли помощника»
  - Работает только по миссии и поручениям ведущего или владельца. Меняющее роль поручение ведущий сначала вносит в состав команды (roster).
  - Дел нет — тишина: не опрашивает, себе задач не придумывает. Пилоты, эксперименты и правки общих файлов (этот навык, CLAUDE.md, README, чужие инструменты) — только после «да» ведущего или владельца.
  - Сдачу проверяют за один круг; повтор того же рода — стоп и вопрос.
  - Команды, способные спросить разрешение, без владельца у экрана не запускать; удаление — списком ведущему.
  - Не хватает данных или неясна норма — вопрос ведущему; затрудняется он — владельца спрашивает он сам (§9). Сам не реконструирует и не придумывает.
  - Владельцу сам не пишет: вопрос — ведущему (§9 «Вопросы владельцу»).
  - Закончил задачу — состояние в файл роли и `clear_session("self")`; внутри задачи — compact.
- **Независимые проверяющие.** Не автор, не исполнитель. Два уровня (решение владельца):
  - **Промежуточные проверки** по ходу задачи: аудит контрактов по триггерам, первичное утверждение данных. Их делают скриптовый разбор сдачи ведущим и проверяющий другой семьи моделей: работу Claude — Codex `gpt-6.1-sol`, работу Codex — субагент Claude Opus единственным проходом ниже (из моделей Claude ревьюит только Opus).
  - **Opus 5.5 `xhigh` (владелец; §0).** Одним брифом в финале перед слиянием или закрытием: аудит контрактов, приёмка и итоговое утверждение данных (§0). Признаки тупика: 3+ итерации без сходимости; второй REJECT или BLOCK того же рода; исполнитель сам пишет, что не может (§0). Opus по ходу работы и на каждый READY не запускается.
  - **Застой (владелец):** 3 ч без закрытого шага принятого PLAN (подпункт с доказательством или принятый DONE; редакции PLAN, ответы на Q, сводки и проверки — не шаги; без PLAN — от первого прогона; считает скрипт) у задачи текущего плана (§3 п. 0) — эскалация исполнителя, но не автоматом: Opus 5.5 `xhigh` (ведущий-Opus или отдельный проход) по хронике и артефактам пишет, почему не движется, и решает: поправка, смена исполнителя (`fleet.md` §4) или перепланирование; до решения новых кругов нет.
  - **Круг задачи (владелец):** на каждом ревью Opus и в каждом проходе заместителя скрипт считает по задаче вопросы и закрытые шаги за 24 и 48 ч; за порогом — разбор всей задачи: Haiku делит вопросы по причинам, Sonnet разбирает вопросы о данных и норме, Opus устраняет причину. Подробно — `fleet.md` «Проверка круга задачи».
  - **Повтор класса (владелец):** вторая странность задачи, оказавшаяся родным поведением движка, — стоп разбора по одной: системный аудит (`checks.md` §6 «Разведка родных механизмов»), не дожидаясь застоя.
  - **Opus проверяет работу, а не выводы** (§3 п. 7).

## 3. Жизненный цикл задачи

0. **Запуск задачи.**
   - **Текущий план.** У проекта один живой список работы; где он — в памяти проекта. 

   Полный текст — `fleet.md`, «Текущий план»

    Запись хранит только текущее состояние: при смене статуса значение заменяют, историю статусов не дописывают. Ведущий обновляет запись при каждом запуске, закрытом шаге и закрытии задачи; по ней сверяют планы исполнителей, застой (§2) и разбор (§10).
   - **Карточка запуска.** До запуска любой задачи (исполнителю, помощнику, армии субагентов как отдельной задаче; субагенты внутри одобренной задачи — без карточки) ведущий пишет карточку файлом и показывает владельцу её суть:
     Полный текст — `fleet.md`, «Карточка запуска»
     - лимиты (§0); были запуски после снимка — снять заново;
     - проверка задания: для задания на проверку или со сложным правилом — пути враждебного чтения и пересказа (п. 1; это подготовка карточки, своей карточки не требует), иначе «не требуется: <почему>»;
     Полный текст — `fleet.md`, «Карточка запуска»
   - Запуск — после ответа владельца. Шаги внутри одобренной задачи нового «да» не требуют; смена подхода или рамки — новая карточка.
1. **Самодостаточное задание.** Задача — issue/CR и пути в репозитории; мост — только канал сообщений. 

   Полный текст — `executor-rules.md`, «Состав задания»

    Починка — класс ошибки, не случай; третья починка по теме за 7 дней — сначала архитектурный пересмотр.
   - **Задание читают буквально (владелец).** Исполнители и субагенты делают задание дословно, противоречие молча обходят, решают по-своему или стоят. Задание — подробное и однозначное: точные пути, рамка правок, исключения из запретов, критерий готовности, чем проверить, что делать при конфликте с кодом («сообщи, тест не ослабляй»). Обязательное для исполнителя правило записывают в задании: ссылку в списке источников он не открывает. Перечитать самому мало: автор своих дыр не видит. Задание на проверку (страж, валидатор, приёмочный тест) или со сложным правилом до запуска (пути результатов — в карточке запуска, п. 0):
     - **сверяется с каталогом ловушек** `briefs.md` в папке навыка;
     - **враждебно читает не автор** (задание Claude — Codex sol): ищет дословное исполнение, при котором запрещённое проходит или честное отвергается, и пишет атаки на цель — входы, которые нарушают цель, и честные случаи, которые должны пройти. Они входят в таблицу доказательства задания красными и зелёными случаями;
     - **пересказывают две модели разных семей**: PLAN и пересказ другой семьи, который PLAN не видит (задание Codex — субагент Claude, и наоборот); сверка — по `briefs.md` «Буквальный язык и организация работы».

     **Буквальный язык (владелец)** — в каждом задании, PLAN и брифе, не только проверочном; правила и проверка — `briefs.md` «Буквальный язык и организация работы»: одно прочтение, записанное намерение, раздел «Организация работы», `tools/check-literal.py --task` и пересказ другой семьи моделей.

   - **Чистый вход (владелец).** Постановщик отвечает, чтобы исполнитель получил только задание, правила проекта и нужные пути. Проверка — скриптом внутри запуска: проба при смене отпечатка запуска (скрипт, конфиг, глобальные файлы, бинарь, папка), отказ при чужом, сверка снятого входа (rollout, запрос) после каждого прогона, с помощниками. Флаги «отключить плагин» не доказывают чистоту — только снятый вход. В нём не должно быть:
     - чужих инструкций: глобальные AGENTS.md/CLAUDE.md домашних папок, чужие skills, внерепозиторные брифы;
     - лишних логов и чужих задач.
   - **Вход субагентов Claude (владелец).** Workflow — только когда последнее сообщение чата — запрос владельца на эту работу, иначе Agent; после запуска — `tools/check-subagent-input.mjs`, FAIL — результаты не принимать. После сдачи субагента Claude ведущий запускает `tools/check-reads.py <журнал.jsonl> <путь[:A-B]>...`; `MISS` или `PART` — результат не принимается.

   Полный текст — `fleet.md`, «Вход субагентов»

   
   - **Субагенты в задании (владелец).** Раздел «Субагенты»: механика списком — поиск, чтение, прогон тестов, выжимки логов, сверки, код по ясному брифу — и для исполнителя или субагента Claude строка «вызови навык `team-process`»; исполнителю Codex эту строку не писать: навыки ему не передаются, правила для исполнителей (`executor-rules.md`) идут текстом задания. Модели — по общим правилам («Субагенты и бюджет»).
   - **Прочитать до работы — с проверкой (владелец).** Ссылку на файл модель сама не открывает — ни исполнитель, ни ведущий; правило «прочитай» работает только вместе с проверкой скриптом.
     - **Список.** Перед заданием, карточкой запуска, PLAN-OK, BENCH-OK и ревью сдачи ведущий выписывает обязательное чтение шага: файлы тем по таблице ядра для его действий и документы проекта (нормы, контракты, решения), на которые шаг опирается.
     - **Ведущий проверяет себя.** До шага — `tools/check-reads.py --deleg-ok <свой журнал> <пути>`: каждый путь `READ` или `DELEG` (поручен субагенту: путь в его промпте) после последнего сжатия контекста. `MISS` или `PART` — шаг не делается, сначала чтение.
     - **Задание.** Раздел «Прочитать до работы»: полные пути `~/.claude/skills/team-process/<файл>` и документов проекта, фраза «прочитай целиком до первого действия». Исполнителю Codex файлы навыка даются текстом нужных правил (файл, раздел), документы проекта — путями.
     - **Исполнитель дополняет сам.** В PLAN — раздел «Чтение»: что прочитано из списка задания, и «не хватает в задании» — правило, норма или контракт, на которые опираются действия задания, но которых нет в списке (ссылка в задании или в прочитанном документе, тема по таблице ядра); их исполнитель читает до PLAN. Пропуск, найденный исполнителем, ведущий в тот же день дописывает ловушкой в `briefs.md`.
     - **Ведущий проверяет исполнителя.** Один раз на задачу, до первого PLAN-OK (владелец), — `tools/check-reads.py` по журналу исполнителя (Claude — журнал сессии, Codex — rollout) на нормативный список задания и раздел «Чтение» (цель — путь или `путь:A-B`; у Codex — и по неусечённым выводам после сжатия, правила — README.md); не проверяются свои файлы исполнителя, логи и изменённые после чтения. `MISS` или `PART` — `PLAN-CHANGES`.
2. **PLAN.** Исполнитель до правок присылает `## PLAN-<id>`: каждое требование своими словами, источник истины, что изменит, чем проверит, развилки с рекомендацией, объём, чего решение не закроет. Два режима:
   - **«План у ревьюера»** — всё, кроме режима ниже, включая тесты и проверки. Исполнитель стоит до `PLAN-OK-<id>`. `PLAN-CHANGES-<id>` — доработать. `PLAN-<id>-delta` отмечает смену подхода по ходу: цели, границ правок, критерия готовности или источника истины; иной внутренний способ реализации нового плана не требует.
   - **«Ведёт sol»** — исследования, черновики данных, разведка. Ведущая модель исполнителя сама делит работу, одобряет внутренние планы, пишет PLAN для записи и не стоит. Стоп только на `DONE` или `Q`. Ревьюер проверяет итог.
   - Без плана — только механические шаги, продиктованные дословно.
   - **Кто делает.** Исполнителя задачи называют в PLAN один раз; у каждого шага указывают колонку «кто делает»: сам, субагент (модель) или скрипт. Нет колонки или механика у «сам» — `PLAN-CHANGES`. Сам отвечает за суждение, план и итоговую сверку; механику поручают субагенту или скрипту. Механика, оставленная себе, — `PLAN-CHANGES`. Цель или результат, которых нет в задании, — тоже `PLAN-CHANGES`; шаги к требуемому результату добавкой не считаются. План исполнителя пишут тем же буквальным языком (§3 п. 1): двусмысленная фраза с разными результатами — тоже `PLAN-CHANGES`. Подпункты без зависимостей или по очереди при возможности параллельной работы — тоже `PLAN-CHANGES`; при PLAN-OK ведущий оценивает критический путь по сверке субагента.
   - **Стенд** (работа опирается на нейросеть: промпт, формат пакета, выбор модели). Полный текст — `bench.md`; читать перед разделом «Стенд» в PLAN и BENCH-OK. Кратко: малый стенд — разделом «Стенд» в PLAN; запуск только по `BENCH-OK` ведущего после его личного разбора провода (SHA `wire-review` и аудита состава); облачная проба первой; пилот формы данных до массового наполнения.
   - **Промпт-ревью** — `checks.md` «Промпт-ревью»: правка промпта, проекции входа или параметров роли сдаётся с `prompt-review-<роль>.md`, ведущий читает его сам и целиком.
3. **OK.** Перед первым `PLAN-OK` задачи ведущий проверяет чтение исполнителя по §3 п. 1 «Прочитать до работы», у исполнителя Claude — ещё и вход `tools/check-subagent-input.mjs`; `MISS` или `PART` — `PLAN-CHANGES`. Отвечай на PLAN быстро: исполнитель простаивает.

   Полный текст — `fleet.md`, «Ответ во время прогона»

   
4. **Работа test-first.** Сначала красный тест, потом код. Самоаудит — один круг (§5).
   - **Надзор (владелец).** Большая задача исполнителя — под надзором ведущего: триггер — закрытый шаг или время из карточки запуска; разведка и сверка с планом — субагентам, решение — ведущему; поправки и помощь, независимое — параллельно; идущую работу не прерывать, поправка — через файл цели; ошибки процесса — в уроки исполнителя. Порядок — `fleet.md` §4 «Надзор за исполнителем».
   - **Приёмочные тесты пишет старшая модель до начала (решение владельца).** Для кодовой задачи — Codex sol, а не исполнитель: до старта, по описанию поведения из задания. Тесты фиксируются хэшем; исполнитель их не меняет (правка — `Q`), неверный тест правит старшая модель. Перед заморозкой тест краснеет по заявленной причине; цель проверяется и поведением в настоящей среде; каждому шагу — свой тест. Подробно — `checks.md` §6 «Приёмочные тесты старшей модели». 5. **DONE.** Блок `## DONE-<id> | время | HEAD <sha>`:

   - числа только из логов, а не из памяти;

   - обязателен раздел «не проверено»; пустым не бывает без пояснения;
   - раздел «Рабочие места» (`cleanup.md` §2);
   - `git status --short`.

Скрипт по транскрипту проверяет, отдавал ли исполнитель механику субагентам, считая вызовы исполнителя и его субагентов (Claude — `tools/usage-daily.py <папка> --session <id>`, Codex — `tools/codex-watch.py`).

## 9. Безопасность и владелец

- Общая машина — §5; чужими сервисами пользоваться как клиент можно, чужие данные не трогать. Секреты и токены не коммитить.
- Запрещены широкие destructive-команды (см. правила проекта): `git clean`, `reset --hard`, `checkout -- .`, `restore .`, `rm -rf .` и любые команды, удаляющие или откатывающие всё дерево рабочей копии.
- **Сначала владельцу.** С явными точками решения ему показывают результаты исследований, каталоги, наборы правил и изменения процесса; только после его OK их вносят в документы, issue и PR и начинают работу по ним. Фильтр аудиторов владельца не заменяет. Рутинное ревью сдач не требует показа ему заранее при разрешённой им автономной работе.
- **Вопросы владельцу и журнал решений.** Пути проекта — в памяти проекта.

  - До вопроса ищи ответ по-русски и по-английски в едином документе проекта, журнале решений, контрактах и правилах; нашёл — ссылка, а не вопрос.

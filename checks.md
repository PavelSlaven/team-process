# team-process — checks (вынесено из SKILL.md; нумерация разделов сохранена)

## 6. Проверки

- **Скрипт вместо модели** (см. общие правила). Сверка счётчиков, diff строк данных, свежесть производных файлов, поиск ссылок — скриптом.
- **Красный → зелёный.** Тест до правки должен падать по нужной причине; иначе он ничего не доказывает.
- **Изоляция.** PR проверяется на чистой копии (`git archive` в пустую папку, а не «в рабочей копии исполнителя»). Два тяжёлых набора одновременно на одной машине не гонять.
  - Рабочую копию, в которой идёт прогон, не менять: ни слияний, ни коммитов, ни checkout, пока прогон не кончился.
  - Урок 2026-10-06: я слил ветку в рабочую копию, пока базовый прогон ждал слота PostgreSQL. Тест стартовал уже на новых файлах, а в логе остался старый HEAD. Базовый прогон — только на копии из `git archive`.
- **«Уже было до меня»** — только после прогона того же теста на базовом коммите в одиночку, без другой нагрузки. Тест, занимающий больше 80% таймаута на базе, чувствителен к нагрузке.
- **Свежесть сгенерированных файлов.** Тест «пересобери и сравни» на каждый генерируемый артефакт (CI сам может свежесть не проверять: main устаревал после слияний, не пересобравших межгрупповые выходы). Изменение файла-владельца — повод прогнать валидаторы зависимых групп, а не только своей; дважды одобрение проходило без этого.
- **После вливания main** дельта пересборки — новое непроверенное содержимое: отдельная короткая проверка, лишний шум вне объёма PR откатить.
- **Конфликты сгенерированных файлов** (каталоги, статусы, журнал изменений) решаются пересборкой или скриптом слияния, не руками.
- **Сторож диффа тестов.** Скрипт показывает изменённые/удалённые утверждения в существующих тестах; любое ослабление — стоп до ответа.
- **Приёмочные тесты старшей модели (решение владельца; кратко — SKILL.md §3 п. 4).** Для кодовой задачи их пишет Codex sol, а не исполнитель: до старта исполнителя, по описанию поведения из задания (что должно работать, что не должно ломаться).
  - Тесты фиксируются хэшем.
  - Исполнитель реализует под них и может добавлять свои тесты, но зафиксированные не меняет. Любая правка такого теста — стоп и `Q`; сторож диффа это ловит.
  - Если зафиксированный тест неверен, его правит старшая модель по `Q` с доводом, а не исполнитель.
  - В финале Opus сам проверяет и тесты (покрывают ли они задание), и работу.
  - Урок: исполнитель раз за разом сужал утверждения ради зелёного прогона.
  - **Перед заморозкой тест краснеет по заявленной причине.** Заявленная причина — конкретный assert или код ошибки, это видно в логе прогона на базе. Тест, который краснеет не там, ничего не доказывает.
  - **Цель — и поведением.** Приёмка проверяет цель в настоящей среде (движок, игра, production-путь), а не только статическим стражем формы: страж закрывает известные обходы, поведение — и неизвестные.
  - **Тест следует модели данных, а не догадке задания.** Перед тестом сверь, где утверждённые данные действительно хранят величину.
  - **Каждому шагу — свой приёмочный тест старшей модели.** Замороженный тест одного шага не закрывает следующий. Если тест среды задаёт шов, production-чтение среды он не проверяет. Перед «продолжай test-first» проверь, покрыт ли шаг замороженным тестом; если нет — сначала тест пишет старшая модель (на прогон переключи модель задачи на sol).
  - **Коммит замороженного теста после DONE меняет объект авто-CA.** Авто-CA этой сдачи уходит в процедурный BLOCK или зависает в очереди: guard видит другой HEAD. Коммить тест до сдачи либо сразу закрывай авто-CA сдачи блоком CLOSE со скриптовой сверкой SHA файла.
- **Тест на production-пути и все потребители формата (урок 2026-10-06, combat-min: 11 раундов CA без сходимости).** Итоговый Opus назвал две причины тупика:
  - тесты строили контекст руками (авторская фикстура), и настоящая композиция не проверялась; CA раз за разом находил дефект на настоящем пути;
  - формат поменяли у производителя, но не у всех потребителей (frozen eval runner читал урезанные messages).
  Приёмка идёт через production-композицию. При смене формата скрипт перечисляет всех читателей поля, и каждый получает тест.
  То же при переносе символов между модулями: паритет тел функций скриптом не ловит потерянную привязку. В 2026-10-07 фасад только реэкспортировал функцию, а сам её вызывал, и получилась ReferenceError. Скрипт перечисляет всех потребителей перенесённого, и все их тесты прогоняются.
- **Валидаторы данных** формулируй по смыслу (одинаковая причина в N местах, сезонность, физика), а не точным совпадением строк: точные проверки исполнитель обходит шаблонным хвостом. Для содержимого по местам — один субагент на место, писать с нуля, общие шаблоны запретить.
- **Счёт шаблонных причин:** перед сравнением вырезай не только id и числа, но и **имя вещи** — иначе «причина = имя + общий хвост» даёт ложную уникальность (урок 2026-09-29: я насчитал 63/63, Opus после вырезания имён — 33).
- **Выборочная независимая проверка** ловит то, что скрипты зелёные пропускают; не отменяй её ради экономии там, где она требуется. Заключение проверяющего вносится в проверяемый артефакт дословно; скриптом проверить: ровно одно вхождение, 0 удалений.
- **Каждый судья пишет, что не так и как исправить (владелец 2026-10-12).** Кроме оценок и вердикта обязательны поля: `dislike` — 1–3 помехи с цитатой; `improve` — 1–3 правки в пределах данных фактов, без новых фактов мира; `missing_facts` — каких фактов не хватает, если без них не улучшить (из них пополняется список пробелов данных и материализации); для набора текстов — `improve_general`, 3–5 правил для рассказчика. Касается судей прозы, стендов и утверждения; REVISE без конкретных правок — неполный ответ, дозапросить у того же судьи.
- **Повторная сборка** производных файлов в отдельной чистой копии с побайтовым сравнением (порядок сборки зависимостей; недетерминизм порядка множеств проверять разными сидами хеша).
- **Типовые дефекты данных:** уверенность выше лучшего источника; неверно приписанные цитаты; устаревшие производные файлы, скрытые жёстко заданными счётчиками; круговые валидаторы (копия проверяется по себе); молча удалённые утверждённые строки; чрезмерное «нет источника», когда ответ есть в собранном. Новое производное правило сверять с уже утверждёнными правилами той же базы: одно правило, а не два.
- **Валидатор владельца отклоняет утверждённые данные (урок 2026-10-07, перенос форм обращения).** Прежде чем ослаблять проверку, сравни скриптом спорное поле с базой.
  - Новое употребление поля (армия писала пояснение пробела в «свидетельство») — чинятся данные: механический перенос по заявленному правилу с детерминированной проверкой. Проверку не трогают.
  - Если устарело само правило проверки (поссылочное вместо построчного; инвариант старого решения, закрытого новым утверждением) — правится проверка, узко и с отрицательными пробами.
  - И сразу проси исполнителя один полный прогон проверки со всеми отказами, сгруппированными по виду, одним вопросом. Иначе выходит по вопросу на каждый вид: здесь было четыре подряд.
- **Армии-исследования: аудит полноты поиска (урок 2026-10-08).** Армия по пробелам знаний сдала «честные пробелы», а независимая проверка нашла 40–59 упущенных наводок на армию. Армия искала только в заранее выбранных книгах, не искала по годам и сюжетам летописи, в FTS не использовала префиксы (мыт*). Кроме того, свидетельства XIII века она записывала как «перенос», не засчитывая их. Поэтому до утверждения сдачи — отдельный проход «полнота поиска»: по одному проверяющему на пункт, каждый сам ищет по индексу. Наводки возвращаются армии: оформить или отвергнуть с причиной.
- **Проверяющий скрипт сам проверяется пробами (урок 2026-10-08).** Общий чекер сдач трижды за день молча пропускал: при упавшем вложенном валидаторе давал PASS; принимал неизвестный question_id; одна запись пробела прикрывала несколько сторон. Нашли исполнители пробами. У каждого общего чекера — самопроверка на подложенных плохих образцах (каждое правило ловит своё), а каждая новая версия — с SHA в NOTE всем исполнителям.
- **Аудит «потерянного» — по документам и по данным (урок 2026-10-06).** Два аудита забытых правил проверяли только документы. Они пропустили собранные, но не утверждённые и нигде не читаемые данные о семье, дворе и старших NPC. Владелец нашёл это сам, прямым вопросом.
  - В объём такого аудита всегда входят каталоги данных и проверка «у данных есть потребитель»:
    - статус таблицы;
    - кто её читает в коде;
    - попадает ли она в импорт.
  - Группа данных, возвращённая на переработку, сразу получает issue на повторное утверждение и подключение. Иначе она выпадает из учёта.
- **Перед PR данных:** нет закоммиченных артефактов сборки (`*.pyc`, `dist/`, `tmp/`); переводы строк не изменены (подсчёт CR скриптом, а не `grep` — в Git Bash он их срезает).
- Синтаксис и формат проверяют инструменты проекта, не модель. После тестов, мутирующих фикстуры, — `git status` и откат неожиданного.

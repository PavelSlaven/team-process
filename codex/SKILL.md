# Рабочий процесс команды (версия для Codex)

Общий процесс для любого проекта в версии для интерактивной сессии Codex владельца: Codex в ней — ведущий-ревьюер, ставит задачи субагентам и исполнителям и проверяет сдачи. Правила проекта (`AGENTS.md` репозитория, governance, аудит контрактов, слияние кода) сильнее этого навыка. «Память проекта» здесь — `AGENTS.md` репозитория и документы, на которые он ссылается; адреса там нет — вопрос владельцу (§9).

Навык — папка `codex/` приватного репозитория `PavelSlaven/team-process`, установленная копией в `~/.codex/skills/team-process`; основная версия (для Claude Code) — корень того же репозитория. Правило меняется в обеих версиях одним коммитом и push в той же задаче. Проектные пути, номера решений и примеры с файлами проекта сюда не пишутся.

Владельцу пишешь по-русски, полным языком, без `caveman`.

## 0. Общие правила владельца, на которые опирается навык

Основная версия берёт их из `~/.claude/CLAUDE.md`; Codex этот файл не читает, поэтому они здесь.

- **Скрипт вместо модели.** Проверки, сравнения, diff, хэши, производные данные, сверка счётчиков, поиск ссылок, валидация форматов, отчёты из фактических результатов — скриптом. Модель — только суждение: авторинг, архитектура, ревью логики. Ставя задачу, сначала спроси: «можно ли это скриптом?»
- **Автор не утверждает сам себя.** Промежуточное утверждение — другая семья моделей (работу Codex — Claude Opus, работу Claude — Codex `gpt-6.1-sol`), итоговое — Opus 5.5 `xhigh`. Работа этой сессии и её субагентов — работа Codex (§2 «Проход Claude»). Механику проверяют тесты, а не утверждение.
- **Модели, новая сессия на задачу, ожидание событием без таймеров и опросов** — §7.
- **Результат длиннее 10 строк** — файлом; наверх статус, путь к файлу и до 10 строк сути.
- **Комментарии в коде.** Категорически запрещено писать комментарий по принципу «полезен, если верен и относится к делу». По умолчанию комментария нет; он должен доказать право на существование: только неочевидное «почему» — инвариант, причина обхода, ссылка на внешнее ограничение. Пересказ кода, планы и история — нет. Внутренние номера находок, планов и решений (`F7`, `A-11b`, `D88`) в комментарий не писать: суть словами. Субагентам и исполнителям этот абзац передавать в бриф дословно.

## 1. Когда применять

- Задачу делает не эта сессия сама, а субагент (`spawn_agent`) или внешний исполнитель (Codex на сервере, Cursor, Claude Sonnet).
- Нужен цикл «задание → план → работа → сдача → ревью → PR».
- Планируешь запуск нескольких агентов, бюджет токенов, ежедневный разбор.
- Не применять: мелкая правка, которую быстрее сделать самому; разовый вопрос.

## 2. Роли

- **Владелец.** Решает по продукту, нормам, необратимому, продакшену; ставит приоритеты. Мелочами не занимать. Решение владельца записывать в тот же день (§9).
- **Ведущий-ревьюер** — эта сессия Codex. Помнит всю цепочку, пишет задания, отвечает на вопросы исполнителей только по технике (продукт, нормы, необратимое и продакшен — владельцу), ревьюит каждую сдачу, ведёт git, PR и слияние по правилам проекта. Не исполнитель: объёмную работу отдаёт субагентам и исполнителям. Ведёт текущий план (§3 п. 0); свой обещанный «следующий шаг — мой» в том же ходе записывает туда, сделал — отмечает (у своего шага нет входящего события).
- **Заместитель ведущего** — если владелец его назначил: делёж по потоку, у дела один хозяин. Ведущий: владелец, нормы, git и слияние, PLAN на контракты, схему БД, промпты LLM, финал. Заместитель: прочие PLAN, BENCH-OK, флот; не сливает.
- **Исполнители.** Субагенты этой сессии (§7); Codex на сервере (руководитель `gpt-6.1-sol` `high`, его субагенты — `gpt-6-luna` `xhigh`; малый аккаунт — только `luna`, разведка); Cursor (`composer-2.5`); Claude Sonnet. Внешний исполнитель — в своей рабочей копии и ветке, общается только файлами задачи (§4).
- **Субагенты Codex** (`spawn_agent`, §7). Чтение, сборы, подсчёты, прогон тестов и выжимки логов, код по ясному брифу, первый проход проверок. Вложенных нет: в брифе строка «своих субагентов не порождай» (инструмент это позволяет, правило — нет). Каждому — своя временная подпапка (§9). Утверждать работу субагент Codex не может (§0).
- **Помощник** — субагент с ролью на время задачи (ревью, тексты, стенды, мониторинг). В его брифе текстом: работает только по брифу и поручениям ведущего; себе задач, пилотов и правок общих файлов (навык, `AGENTS.md`, README, чужие инструменты) не делает; проверка сдачи — один круг, повтор того же рода — вопрос ведущему; команды, способные спросить разрешение, не запускает, удаление — списком ведущему; нет данных или неясна норма — вопрос ведущему, сам не придумывает, владельцу не пишет.
- **Любой план ведущего, разбор очереди или оптимизация называет исполнителя каждого пункта среди всей команды:** субагенты, внешние исполнители, скрипты, владелец — а не только ведущий.
- **Независимые проверяющие.** Не автор, не исполнитель. Два уровня (решение владельца):
  - **Промежуточные проверки** по ходу задачи: аудит контрактов по триггерам, повторные раунды после исправлений, первичное утверждение данных. Их делают скриптовый разбор сдачи ведущим и проверяющий другой семьи моделей: работу Codex — Claude Opus, работу Claude — Codex `gpt-6.1-sol` (из моделей Claude ревьюит только Opus).
  - **Opus 5.5 `xhigh` сверх промежуточной проверки работы Codex — только в двух случаях.** (1) Финал: приёмка перед слиянием или закрытием задачи, итоговое утверждение данных. (2) Тупик: исполнитель не может решить проблему. Признаки тупика: 3+ итерации без сходимости; второй REJECT или BLOCK того же рода; исполнитель сам пишет, что не может. Opus по ходу работы и на каждый READY не запускается.
  - **Застой:** 3 ч без закрытого шага у задачи в работе по текущему плану (§3 п. 0) — отдельный аудитор застоя (Opus 5.5 `xhigh`): почему не движется процесс; новых кругов до вердикта нет. Ведущий сверяет время последнего закрытого шага при старте сессии, каждом запуске и закрытии.
  - **Opus проверяет работу, а не выводы** (§3 п. 7).
- **Проход Claude.** Из сессии Codex Claude не запускается. Для прохода другой семьи (утверждение, враждебное чтение и пересказ задания, финал, тупик, застой) ведущий пишет пакет файлом (вопрос, задание, исходный план, diff, артефакты — §3 п. 7) и даёт владельцу путь и строку «что проверить»; запускает владелец или ведущий Claude. До вердикта работа не утверждена; продолжать — только шаги, от вердикта не зависящие.

## 3. Жизненный цикл задачи

0. **Запуск задачи.**
   - **Текущий план.** У проекта один живой список работы; где он — в памяти проекта. В нём цель, задачи по порядку, у каждой исполнитель, статус, время последнего закрытого шага и что ждёт владельца. Запись задачи хранит только текущее состояние: при смене статуса значение заменяется, история статусов не дописывается. Ведёт ведущий: правит при каждом запуске, закрытом шаге и закрытии задачи. По нему сверяют планы исполнителей, застой (§2) и разбор (§10).
   - **Карточка запуска.** До запуска любой задачи (внешнему исполнителю, помощнику, армии субагентов как отдельной задаче; субагенты внутри одобренной задачи — без карточки) ведущий пишет карточку файлом и показывает владельцу её суть:
     - что и зачем — пункт текущего плана;
     - как — шаги: кто делает, модель и `reasoning_effort`, что на выходе и в какой форме (п. 2, п. 5);
     - источник истины по каждому пункту;
     - лимиты Claude и Codex числами, с временем снимка (§7); были запуски после снимка — снять заново;
     - проверка задания: для задания на проверку или со сложным правилом — пути файлов враждебного чтения и пересказа (п. 1; это подготовка карточки, своей карточки не требует), иначе «не требуется: <почему>»;
     - вопросы владельцу (§9), у каждого — где искал ответ;
     - чего задача не делает.
   - Запуск — после ответа владельца. Шаги внутри одобренной задачи нового «да» не требуют; смена подхода или рамки — новая карточка.
1. **Самодостаточное задание.** Задача = issue/CR в репозитории + пути в репозитории; мост только канал сообщений. В задании: цель, источник истины по каждому пункту, что не трогать, чем проверять, режим (п. 2), правила из §5. Задача по логике продукта — раздел «Механизм и владелец»: общий механизм, владелец, почему не частный случай, ≥3 разных случая класса. Починка — класс ошибки, не экземпляр; третья починка одной темы за 7 дней — сначала архитектурный пересмотр.
   - **Задание читают буквально (владелец).** Исполнители и субагенты делают задание дословно, противоречие молча обходят, решают по-своему или стоят. Задание — подробное и однозначное: точные пути, рамка правок, исключения из запретов, критерий готовности, чем проверить, что делать при конфликте с кодом («сообщи, тест не ослабляй»). Обязательное для исполнителя правило — текстом в задании: ссылку в списке источников исполнитель не открывает. Перечитать самому мало: автор своих дыр не видит. Задание на проверку (страж, валидатор, приёмочный тест) или со сложным правилом до запуска (пути результатов — в карточке запуска, п. 0):
     - **сверяется с каталогом ловушек** `references/briefs.md`;
     - **враждебно читает не автор** (задание этой сессии — Claude, §2 «Проход Claude»; задание Claude — Codex sol): ищет дословное исполнение, при котором запрещённое проходит или честное отвергается, и пишет атаки на цель — входы, которые нарушают цель, и честные случаи, которые должны пройти. Они входят в таблицу доказательства задания красными и зелёными случаями;
     - **пересказывают две модели разных семей**: PLAN исполнителя и независимый пересказ другой семьи, который PLAN не видит (задание Codex — Claude, и наоборот). Ведущий сверяет их до `PLAN-OK`; расхождение в понимании — дыра в тексте: правится задание, а не план.

     **Буквальный язык (владелец).** Задание и план пишутся так, чтобы каждое требование допускало одно прочтение — то, которое имел в виду постановщик. Вместо слов «по возможности», «при необходимости», «и т. п.», «и подобное», «аналогично», «как обычно», «как сейчас», «разумно», «где уместно», «лучше» — точный список, условие или число. Вместо «это», «там», «такой», «он» без ясного предмета — название предмета. Каждое действие называет объект, место (путь файла и раздел или строку в нём; для команды — рабочую папку) и признак выполнения. Перед отправкой постановщик перечитывает каждую фразу с вопросом «можно ли выполнить это иначе, чем я имею в виду?»; если можно — переписывает фразу (дословную цитату владельца не меняет — уточняет рядом).

   - **Чистый вход (владелец).** Постановщик отвечает, чтобы исполнитель получил только задание, правила проекта и нужные пути; флаги «отключить плагин» чистоту не доказывают — только снятый вход. Проверка у внешнего исполнителя — `references/fleet.md` §4 «Чистый вход».
   - **Вход субагентов Codex (владелец).** `spawn_agent` — всегда с `fork_turns: "none"`: значение по умолчанию `"all"` копирует субагенту весь чат ведущего, то есть чужой вход. Бриф — файлом в рабочей папке задачи, в `message` — путь к брифу и одна строка задачи: после сжатия контекста у субагента остаётся пересказ сообщения, а не его текст. Результат субагента с чужим или неизвестным входом не принимается.
   - **Субагенты в задании (владелец).** Раздел «Субагенты»: механика списком — поиск, чтение, прогон тестов, выжимки логов, сверки, код по ясному брифу — и для исполнителя или субагента Claude строка «вызови навык `team-process`»; исполнителю Codex и субагенту этой сессии эту строку не писать: навыки им не передаются, правила для исполнителей (`references/executor-rules.md`) идут текстом задания. Модели — по §7.
2. **PLAN.** Исполнитель до правок присылает `## PLAN-<id>`: каждое требование своими словами, источник истины, что изменит, чем проверит, развилки с рекомендацией, объём, чего решение не закроет. Два режима:
   - **«План у ревьюера»** — всё, кроме режима ниже, включая тесты и проверки. Исполнитель стоит до `PLAN-OK-<id>`. `PLAN-CHANGES-<id>` — доработать. Смена подхода по ходу — `PLAN-<id>-delta`; смена подхода — это смена цели, границ правок, критерия готовности или источника истины, а другой внутренний способ реализации нового плана не требует.
   - **«Ведёт sol»** — исследования, черновики данных, разведка. Ведущая модель исполнителя сама делит работу, одобряет внутренние планы, пишет PLAN для записи и не стоит. Стоп только на `DONE` или на `Q`. Ревьюер проверяет итог.
   - Без плана — только механические шаги, продиктованные дословно.
   - **Кто делает.** Исполнитель задачи назван в PLAN один раз; шаги, отданные субагенту (с моделью) или скрипту, перечислены отдельно вместе с их исполнителем. Сам — суждение, план, итоговая сверка; механика — субагенту или скрипту. Механика, оставленная себе, — `PLAN-CHANGES`. План добавляет цель или результат, которых нет в задании, — тоже `PLAN-CHANGES`; шаги реализации требуемого результата добавкой не считаются. План исполнителя пишется тем же буквальным языком (п. 1): фраза плана, которую можно понять двумя способами с разным результатом, — тоже `PLAN-CHANGES`.
   - **Стенд** (работа опирается на нейросеть: промпт, формат пакета, выбор модели). Полный текст — `references/bench.md`; читать перед разделом «Стенд» в PLAN и перед BENCH-OK. Кратко: малый стенд — разделом «Стенд» в PLAN; запуск только по `BENCH-OK` ведущего после его личного разбора провода (SHA `wire-review` и аудита состава); облачная проба первой; пилот формы данных до массового наполнения.
   - **Промпт-ревью.** Каждое изменение промпта, проекции входа роли или параметров роли сдаётся с `prompt-review-<роль>.md`: полный system + user + params «до/после», снятые из фактического запроса к провайдеру. Ведущий читает его лично и целиком (не субагент) до CLOSE и коммита; замечания возвращает с файл:строка.
3. **OK.** Отвечай на PLAN быстро: исполнитель простаивает. Ответ, отправленный во время прогона, исполнитель не увидит — отправляй после остановки (§4).
4. **Работа test-first.** Сначала красный тест, потом код. Самоаудит — один круг (§5).
   - **Приёмочные тесты пишет старшая модель до начала (решение владельца).** Для кодовой задачи — Codex sol до старта исполнителя, по описанию поведения из задания; тесты фиксируются хэшем, исполнитель их не меняет (правка — `Q`). Подробно — `references/checks.md` §6 «Приёмочные тесты старшей модели».
5. **DONE.** Блок `## DONE-<id> | время | HEAD <sha>`:
   - журнал хода как есть (строка на подпункт: что сделано, коммит, тест) и строки вывода проверок — красный до правки и зелёный после; отдельной таблицы нет;
   - числа только из логов, а не из памяти;
   - раздел «не проверено» (обязателен, пустой не бывает без пояснения);
   - `git status --short`.
6. **Ревью скриптами.** Ведущий проверяет сдачу детерминированно (§6), а не «прочитал и поверил». Заявленный зелёный прогон без лога — не прогон. Изменения данных ведущий строит скриптом из двух версий (id, столбец, старое → новое); изменение строки данных, которого не требует задание и не объясняет пересборка производных файлов, — дефект сдачи. Проверяя, отдавал ли исполнитель механику субагентам, ведущий сам считает скриптом по транскрипту вызовы исполнителя и его субагентов (у Codex — его `rollout-*.jsonl`; путь у внешних исполнителей — в памяти проекта).
7. **Независимая проверка** — по уровням §2. Автор не утверждает себя.
   - **Opus: один проход в финале или при тупике** (передача — §2 «Проход Claude»). Проверяет не только DONE и выводы исполнителя, но и саму сделанную работу. Пакет Opus: diff; сами артефакты — промпты и входы ролей, снятые с провода (`prompt-review-<роль>.md`), строки данных, случаи стенда, сырые ответы модели, логи прогонов; задание и исходный план.
   - **Opus обязан** открыть артефакты сам и выборочно проверить качество работы по существу, воспроизвести ключевые цифры, в вердикте ссылаться на файл:строку артефакта, а не на текст сдачи. Вердикт, опирающийся только на DONE, — не проверка.
   - **При тупике Opus** сначала ищет, не в работе ли исполнителя причина: промпт, проекция, данные, стенд. Только потом — в модели или задаче.
8. **PR → CI → слияние** (§8).
   - **Закрытие.** Сразу после слияния или приёма исследования — отметка в текущем плане (п. 0) и закрытый issue. В режиме флота ещё блок `## CLOSE-<id> | время | принято; слито в #N` в мост: без него задача остаётся на доске «ждёт ревьюера».
9. **BLOCK / rework.** Ответ `REVIEW-<id>` с точными пунктами и путями (файл:строка, что не так, что ожидается). Не «переделай», а список.
   - **Причина каждого REJECT и BLOCK.** В вердикте — поле «причина»: задание, исполнитель, приёмочный тест, данные или среда; его заполняет проверяющий (строка в каждом брифе проверки). Причина «задание» — ведущий в тот же день дописывает ловушку (ловушка, пример, как писать) в `briefs.md` обеих версий. При закрытии задачи (п. 8) ведущий сверяет: у каждого возврата есть причина в журнале причин проекта, у причины «задание» — ловушка в `briefs.md`.
10. **Стоп-правила.**
    - Повторный обход того же рода (второй раз то же самое) — стоп и вопрос `Q`, а не третий круг.
    - Исполнитель повторно ослабляет проверки, чтобы получить зелёное, — замена исполнителя.
    - Блокирующий вопрос — `## Q-<id>-NN` и стоп.
    - Тупик (признаки — §2) — не ещё один круг, а эскалация: проход Opus по артефактам работы (§2, §3 п. 7) и решение ведущего — перепланировать, сменить исполнителя или вынести владельцу.

## 9. Безопасность и владелец

- Общая машина — по `references/executor-rules.md`; чужими сервисами пользоваться как клиент можно, чужие данные не трогать. Секреты и токены не коммитить.
- Широкие destructive-команды запрещены (см. правила проекта): `git clean`, `reset --hard`, `checkout -- .`, `restore .`, `rm -rf .` — и любая команда, которая удаляет или откатывает всё дерево рабочей копии.
- **Сначала владельцу.** Результаты исследований, каталоги, наборы правил, изменения процесса показываются владельцу с явными точками решения; в документы, issue и PR они попадают, и работа от них запускается, только после его OK. Фильтр аудиторов владельца не заменяет. Рутинное ревью сдач при разрешённой владельцем автономной работе можно проводить без предварительного показа владельцу.
- **Вопросы владельцу и журнал решений** (пути — в памяти проекта). Задаёт только ведущий; субагенты и исполнители передают вопрос ему. До вопроса — поиск ответа: единый документ проекта, журнал решений, контракты и правила, по-русски и по-английски; нашёл — ссылка, а не вопрос. Вопрос — кратко: контекст 1–3 строки, где искал, варианты и рекомендация первой; пачкой, сложное — файлом. Ответ — дословно в тот же день в журнал решений проекта и в репозиторий (по продукту — журнал решений продукта, процессное — issue или комментарий), не только в чат или мост. Ответа нет или «позже» — пункт в реестр открытых вопросов; предложение ведущего помечено как предложение.
- **Каждая найденная проблема и всё отложенное — свой issue в тот же день (решения владельца).** Считаются находки аудитов (включая аудит контрактов), ревью, стендов, прогонов и ежедневного разбора и всё, что решено «позже», «на следующем этапе» или «после X». Без отдельного issue — только находка ревью, которую исправляют в той же задаче до её закрытия. В issue: что не так или что отложено; почему; условие возврата; источники (файл:строка). Строки в отчёте, мосте или общем плане недостаточно. Исполнитель перечисляет находки вне задачи в сдаче, issue заводит ведущий. Общий план не закрывает отложенные пункты: каждый закрывается, когда решён.
- **Отказ песочницы или запрос разрешения** не обходить: объяснить владельцу, что заблокировано и почему, и ждать решения.
- **Субагенты и временные папки.** В каждом брифе, разрешающем временные файлы: своя подпапка `<временная папка задачи>/<метка>/`, «удалять только её, ничего другого во временной папке не трогать».
- Каждому решению владельца «да» сопоставлять пункт — не додумывать шире сказанного.

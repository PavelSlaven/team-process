# team-process — lessons (вынесено из SKILL.md; нумерация разделов сохранена)

## 11. Уроки (по строке)

- В Git Bash на Windows `python3` бывает заглушкой Microsoft Store, которая ничего не делает: скрипт правки запускать через `python3` на сервере или через `node`; после запуска проверять содержимое целевого файла и наличие ожидаемого изменения.
- Время в отчётах брать из логов и `date`, не придумывать.
- При изменённых режимах файлов (например, после `npm ci`) в рабочей копии исполнителя выполнить `git config core.fileMode false`; изменения режима не коммитить.
- В каждом пункте задания указывать источник истины и способ проверки.
- Скрипты, написанные на Windows для сервера, — только с LF (`sed -i 's/\r$//'`); каталог, скопированный с Windows `tar`, оставляет чужого владельца и ломает песочницу исполнителя (`--no-same-owner` или `chown`).
- Ответ ревьюера, пришедший во время прогона, исполнитель в этом прогоне не видит: инструмент связи ставит продолжение в очередь, а исполнитель перед DONE перечитывает ответы.
- Старшую модель — только для плана и короткого суждения, работу — младшей (SKILL.md §7); сжатие и смена сессий — по `fleet.md` §7.
- Время в заголовках сообщений и отчётов процесса (например, `## DONE-<id> | время`) ставит инструмент записи, а не модель.
- Авторинг данных не запускать, пока по пункту идёт архитектурный разбор или открыт вопрос владельца.
- Валидаторы и checker'ы групп данных считать тестами: контрольный скрипт диффа должен охватывать и их, а сдача данных — запускать self-test каждой группы.
- После второго REJECT того же рода — смена исполнителя, а не третий круг.
- После правки инструмента под таймером systemd запускать его без `HOME` и окружения входа, как таймер: `env -i PATH=… <команда>`; журнал юнита (`journalctl -u …`) проверять на FAILURE, в вечернем разборе тоже.
- Перед отрицательным выводом об отсутствии проверки или механизма прочитать путь вызова.
- Если исполнителей приостанавливают, выставив 0 слотов, проверить, что обязательный этап каждого цикла инструмента флота завершается с кодом 0 и доставка готовых ответов продолжается.
- Каждое обязательное правило запуска, включая проверки после запуска, — отдельным полем карточки запуска (SKILL.md §3 п. 0).
- У каждого механизма процесса (таймер, монитор, хук, ручная процедура роли) — назначенный исполнитель, чья работа проверена, и сигнал ведущему, если механизм не сработал.
- В тексте хука `SessionStart` после сжатия указывать «если ты субагент, пропусти»; бриф субагента передавать файлом.
- Срока на разведку и PLAN не ставить: срок режет качество разведки. Медленный план лечится шириной, а не сроком: разведку делить на независимые части и запускать параллельно до предела среды — у Codex `max_concurrent_threads_per_session` в обёртке запуска по ресурсам сервера, у Claude разведчики Haiku до предела Workflow.

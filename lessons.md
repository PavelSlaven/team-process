# team-process — lessons (вынесено из SKILL.md; нумерация разделов сохранена)

## 11. Уроки (по строке)

- Блок, вставленный в середину файла моста, прячется от монитора: только дозапись в конец.
- Апостроф в heredoc внутри `ssh '...'` обрывает кавычку: писать файл, `scp`, `cat >>`.
- `python3` в Git Bash на Windows — заглушка магазина: молча ничего не делает. Запускать на сервере или на node; проверять, что правка реально произошла.
- Фальшивые таймстемпы в отчётах: время брать из логов и `date`, не придумывать.
- «`git status` чисто» при изменённых режимах файлов: отключить `core.fileMode` в среде исполнителя и не коммитить chmod.
- Подгонка под точные валидаторы (шаблонный хвост, ослабленный тест): валидатор по смыслу, сторож диффа тестов, выборочная независимая проверка.
- «Уже было до меня» — только на изолированной базе, одиночным прогоном.
- Повтор «фикса» одного и того же рода по кругу — сигнал остановиться и спросить, а не третья итерация.
- Ответ, отправленный во время прогона, теряется до следующего возобновления.
- Смена инструмента, который вызывает работающий монитор, запускает побочные эффекты — сперва остановить монитор.
- Проверил только свой набор данных — пропустил устаревание зависимого: после правки владельца прогонять валидаторы зависимых наборов.
- Расплывчатое «проверь независимо» в задании рождает самодельный парсер и круги самоаудита: в каждом пункте задания указывать, где источник истины и чем проверять.
- Скрипты, написанные на Windows для сервера, — только с LF (`sed -i 's/\r$//'`); каталог, скопированный с Windows `tar`, оставляет чужого владельца и ломает песочницу исполнителя (`--no-same-owner` или `chown`).
- Сдача с «зелёным» без лога: числа только из логов, иначе возврат.
- Записка во время прогона теряется (09-29: 15 из 22): инструмент сам ставит продолжение в очередь, если ответы выросли за прогон; исполнитель перечитывает ответы перед DONE.
- Дорогая модель в роли исполнителя съедает недельный лимит (09-29: sol ≈3000 кредитов против ≈60 у всех luna): дорогая — только план и короткое суждение, работа — дешёвая; разросшаяся сессия — новая с передачей.
- Старшая модель как первый фильтр дорога (09-29: 25 из 38 проходов Opus — доработка): сначала скрипт шаблонов и сторож тестов, потом старшая модель.
- Время в заголовке ставит инструмент, а не модель: ручное время уезжает до полутора часов.
- Авторинг данных не запускать, пока по пункту идёт архитектурный разбор или открыт вопрос владельца: иначе работа выбрасывается (09-29: каталоги порядковых подписей и подписей по месту назначения).
- Задание «в сессии» (cron сессии) умирает с перезапуском: регулярные обязанности — постоянной плановой задачей приложения.
- Сторож только тестовых файлов пропускает ослабление проверок данных: удалённую проверку валидатора, строку в checker, из-за которой расхождения исчезают, «ожидания», подогнанные под данные. Валидаторы и checker'ы групп данных — тоже тесты. Сторож должен смотреть и их, а сдача данных — запускать self-test каждой группы.
- Дешёвый исполнитель на тонкой ревизии данных дважды подряд повторил дефекты того же рода (формат, неполное окружение, источники не поискал, очередь только текстом). После второго REJECT того же рода — смена исполнителя, а не третий круг.
- Скрипт под таймером systemd живёт без `HOME` и без окружения входа. С `set -u` одна строка с `$HOME` 17 часов роняла каждый тик: доска и снимки мостов стояли, и никто не заметил (2026-09-30). После правки инструмента запускай его как таймер: `env -i PATH=… <команда>`. Журнал юнита (`journalctl -u …`) проверяй на FAILURE, в вечернем разборе тоже.
- Отрицательный вывод «проверки/механизма нет» по `grep` строки в одном файле — ложный, если механизм подключён импортом (10-05: «BENCH-OK в `bench-request` нет» при установленном `bench_approval.py` → лишняя пауза стендов, такт флота «устарел», результаты не доставлялись). Перед «нет» — прочитать путь вызова.
- Пауза через «0 слотов» может быть ошибкой для инструмента: проверить, что обязательный этап такта при этом завершается с 0 и продолжает доставку готового.
- Расход лимита Claude определяет размер контекста, а не модель и не число задач: 88–92% — перечитывание контекста. Первое средство — потолок контекста и запрет холостых ходов (§7), затем скрипты-выжимки и субагенты с результатом в файл (замер 2026-10-12).
- План, который писал или правил сам исполнитель, до исполнения проверяет независимая роль по главному правилу проекта; само правило, СТОП при готовом аналоге и запрет своих порогов и бюджетов — в тексте задания: ссылку в списке источников исполнитель не откроет.
- Чистый вход: AGENTS.md администрирования сервера подмешивался почти во все сессии Codex — фактический вход проверять скриптом.
- Форма входа случаев: приметы без пола при описании «мужчина» дали аудитору законный повод отклонять — payload случая сверять с production-проводом.
- Вход стенда: в fixc2-14 стенд выдумал «дыхание», союзника и сцену и выбросил здоровье и характер — три круга ревью не поймали; первым шагом — таблица «поле | контракт | код | стенд».
- Фактор во входе: в N1 «отношение к собеседнику» шло только кодом `peer|senior`, system о нём молчал, а провал по этой оси приписали модели.
- Красный не там: npc-claims прошёл два аудита «по смыслу», а упал раньше нужного места.
- Тупик: «Qwen не справляется» оказалось виной исполнителя — английские промпты, сырой JSON с id, planner на 44.5k символов (`local-model-context-rules.md`).
- Замена исполнителя: после четвёртого ослабления теста задача ушла другому исполнителю.
- Правило, у которого нет точки срабатывания, живёт, пока о нём помнят: враждебное чтение заданий делали 10-21…10-22, а с 10-23 ни одно из 13 заданий на проверку его не получило. Каждое правило запуска — полем карточки запуска (§3 п. 0).
- Механизм на спящей роли или выключенном расписании молча умирает: причины возвратов разобраны у 2 вердиктов из 30, часы застоя показывали STALL 144 ч, вечерняя проверка не дала ни одного отчёта. У механизма — исполнитель, который точно работает, и сигнал о провале.
- Хук `SessionStart` после сжатия срабатывает и в субагентах: команда «восстанови роль распорядителя» пришла трём субагентам-сборщикам (10-27), они её отклонили. В тексте хука — «если ты субагент, пропусти»; бриф субагента — файлом.
- Workflow передал агентам ревью ответ владельца на другую тему («1,3,4,6,7») как «голос пользователя» сильнее задания: агенты сделали только эти пункты и пропустили 2 и 5. Из 72 запусков сессии такое сообщение получили 24 (415 агентов), из них один — служебный отчёт сессии-потомка. Правило и скрипт — §3 п. 1 «Вход субагентов Claude».
